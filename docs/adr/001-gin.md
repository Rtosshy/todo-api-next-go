# 001 Gin

- Status: Accepted
- Date: 2026-04-30
- Supersedes: None
- Superseded by: None

## Context

<!--
なぜこの決定が必要になったのか。
前提、制約、課題を書く。
-->

- todoアプリケーションを作る上でRESTの通信が必要になる
- 個人開発兼学習目的のプロジェクトであり、フレームワーク選定で時間を使うより実装で手を動かすことを優先したい
- 学習リソース（記事・チュートリアル）が豊富で、詰まったときに情報が得やすいRESTフレームワークが必要

## Decision

<!--
何を決めたのか。
できるだけ短く、明確に書く。
-->

- フレームワークにgin-gonic/Ginを採用する

## Rationale

<!--
なぜその決定にしたのか。
判断基準、重視したことを書く。
-->

- 学習目的として、既に触った経験のあるEchoではなく未経験のGinを選び、新しいフレームワークに触れる機会としたかった
- 当時参照していた学習コンテンツ・チュートリアル・記事の多くがGinを採用しており、詰まったときの情報量も担保されていた
- 開発を進めた結果、gin-contribエコシステムやoapi-codegen / gin-swaggerとの連携で困ることはなかった。ただしこれらはEchoでも同等に成立するため、Gin固有の優位性ではない

## Consequences

<!--
この決定によって起きる影響を書く。
良い影響だけでなく、受け入れる制約や運用負荷も書く。
-->

- 良い影響
  - 学習リソースが豊富でエラー時の自己解決がしやすい
  - gin-contrib（cors, timeout, zap）やoapi-codegen/gin-middlewareなど周辺ライブラリが揃っており、追加機能の実装コストが低い
- 受け入れる制約
  - 個人todoアプリのスコープに対してGinの機能セット（HTMLテンプレート、各種レンダラ、複雑なバインディング等）はオーバースペック気味で、利用していない機能が多い
  - ハンドラ層が`*gin.Context`に依存するため、将来別フレームワークへ移行する際はハンドラの書き換えが必要
  - Gin v2のメジャーアップデート時に移行コストが発生し得る
- 振り返りでの学び
  - 機能・エコシステム観点ではEchoとの差はほぼなく、フレームワーク選定が成果に与える影響は事前に懸念したほど大きくなかった。次回以降の類似選定では過剰に悩まないという判断材料になる

## Alternatives Considered

<!--
検討したが採用しなかった選択肢を書く。
それぞれを不採用にした理由も書く。
-->

- Echo: 過去に触った経験あり。機能・API・エコシステム（oapi-codegen, zap連携を含む）ともにGinと同等で有力候補だったが、学習目的として未経験のフレームワークを試したかったため不採用。機能面での優劣で落としたわけではない
- net/http（標準ライブラリのみ）: 当時参照していた学習コンテンツがnet/httpを直接使っていなかったため、学習効率の観点で却下
- Fiber / chi: 候補として名前は認識していたが、詳細な比較調査は行っていない
