# 002 GORM

- Status: Accepted
- Date: 2026-04-30
- Supersedes: None
- Superseded by: None

## Context

<!--
なぜこの決定が必要になったのか。
前提、制約、課題を書く。
-->

- todoアプリケーションでRDBへの永続化が必要になり、DBアクセス層の方針を決める必要があった
- 個人開発兼学習目的のプロジェクトであり、生SQLを書き続けることによる心理的ハードルを下げ、実装の手を止めない選択をしたい
- マイグレーションの仕組みとトランザクション境界の引き方も併せて決める必要があった

## Decision

<!--
何を決めたのか。
できるだけ短く、明確に書く。
-->

- DBアクセス層にGORMを採用する

## Rationale

<!--
なぜその決定にしたのか。
判断基準、重視したことを書く。
-->

- ORMによってSQLを直接書くハードルが下がり、CRUDの実装速度を優先できる
- 学習目的として一度GORMを使ってみたかった
- AutoMigrate / Migratorによるマイグレーション運用が手軽で、個人開発のスコープに合う
- `db.Transaction`によるトランザクション境界の引き方が分かりやすく、サービス層からの呼び出しがシンプルに保てる

## Consequences

<!--
この決定によって起きる影響を書く。
良い影響だけでなく、受け入れる制約や運用負荷も書く。
-->

- 良い影響
  - CRUDコードが短く書け、SQL構文に詰まることによる実装停滞がない
  - マイグレーションをアプリ側で完結させられ、別ツールを導入する必要がない
  - トランザクション境界がコードから読み取りやすい
- 受け入れる制約
  - リフレクションベースのSQL生成によるランタイムオーバーヘッドを許容する（個人todoアプリのスコープでは問題にならないと判断）
  - 生成SQLが暗黙的になりやすく、パフォーマンス問題が出た場合は`Debug()`やログで実SQLを確認する運用が必要
  - 複雑なクエリやN+1の制御は素のSQLより注意が要る

## Alternatives Considered

<!--
検討したが採用しなかった選択肢を書く。
それぞれを不採用にした理由も書く。
-->

- database/sql + 生SQL: 透明性は最も高いが、SQLを都度書くハードルが実装速度を下げると判断して不採用
- sqlc: 型安全なクエリ生成として有力だったが、今回は「ORMを一度使ってみる」という学習動機を優先したため不採用
- ent: 一度試そうとしたが、スキーマ定義やコード生成の理解が追いつかず使いこなせなかったため不採用
- bun / sqlx: 候補として認識はしていたが、詳細な比較調査は行っていない
